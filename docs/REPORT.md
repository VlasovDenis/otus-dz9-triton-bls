# DZ9: результаты нагрузочного тестирования

## Среда и метод

- GPU: RTX 3070 Laptop, 8 GiB; загрузка GPU во время прогона пока не зафиксирована.
- Triton: образ 26.08, четыре модели в статусе READY.
- Генерация: Qwen2.5-0.5B-Instruct, FP16, до 64 токенов.
- Эмбеддинги: paraphrase-multilingual-MiniLM-L12-v2, Python Backend на CPU.
- Классификатор: демонстрационная ONNX модель на CPU с dynamic batching.
- Нагрузка: Perf Analyzer из образа 26.08-py3-sdk, gRPC, batch size 1, concurrency 1–4. В первом прогоне окно длилось 10 секунд; генератор тестировался с `--streaming`, ветки BLS — синхронными запросами.
- Повторный прогон ветки вопроса: `--measurement-mode=count_windows --measurement-request-count=30 --stability-percentage=20`. Для каждого concurrency подтверждено 90 запросов. Остальные строки используют стандартный порог стабильности 10%.
- Источник измерений: консольные выводы двух прогонов от 30.09.2026. Логи на тестовом хосте лежат в `artifacts/perf/*.log`, включая `assistant_bls_question_retry.log`; их следует приложить к сдаче.

## Наблюдения

- Для ветки вопроса вычисление занимает около 1.5–1.8 с, потому что BLS ждёт результат генерации. При росте concurrency с 1 до 4 throughput увеличивается лишь с 0.55 до 0.65 RPS, а средняя очередь BLS — с 0.13 мс до 4557.44 мс. При concurrency 4 очередь составляет примерно 75% средней задержки 6092.04 мс.
- По конфигурации у `assistant_bls` один CPU-экземпляр, а его `execute` синхронно ждёт генератор. Пока он ждёт ответ, следующие запросы в BLS остаются в очереди. Это главный измеренный предел полной цепочки при высокой конкуренции. Прямой вызов генератора при concurrency 4 достиг 2.50 RPS, но входной prompt в прямом тесте отличается от prompt внутри BLS, поэтому цифры не дают точной оценки ускорения после изменения BLS.
- Для ветки сообщения генерации нет: при concurrency 1 её средняя задержка 17.88 мс близка к 16.42 мс эмбеддинга. При concurrency 4 очередь BLS выросла до 59.93 мс, а throughput не вырос относительно concurrency 1.
- ONNX классификатор существенно быстрее остальных этапов. Рост RPS при concurrency 4 согласуется с работой dynamic batching, но на малом демонстрационном классификаторе влияние прогрева и накладных расходов велико; его нельзя переносить на другие модели.
- RPS отдельных моделей нельзя суммировать как RPS всей цепочки. Длина генерации влияет на задержку.

## Ограничения и дополнительные артефакты

Данных о загрузке GPU/CPU именно во время этих прогонов ещё нет. Перед сдачей сохранить `nvidia-smi` во время генерации и метрики Triton командой `curl --noproxy 127.0.0.1 -fsS http://127.0.0.1:8002/metrics > artifacts/perf/metrics.prom`. Предупреждение об отсутствии GPU-драйвера в контейнере SDK относится к генератору нагрузки, который посылает запросы по gRPC, и само по себе не говорит о режиме работы контейнера Triton. Версии или ревизии скачанных весов следует записать в финальной версии отчёта.

## Сравнение с отдельным Flask/FastAPI-сервисом

Triton даёт общий gRPC/HTTP API, встроенные очереди и метрики, версионный репозиторий моделей и dynamic batching для ONNX модели. BLS оставляет маршрутизацию вопроса и сообщения внутри сервера. Аналогичную функциональность можно реализовать в FastAPI, но очереди, вызовы моделей, метрики и жизненный цикл нескольких бэкендов придётся конфигурировать отдельно. Это качественное сравнение возможностей: сравнительного нагрузочного теста с Flask/FastAPI здесь нет.

Первой оптимизацией для ветки вопроса проверить `instance_group { kind: KIND_CPU count: 2 }`, затем `count: 4` у `assistant_bls`: несколько экземпляров смогут одновременно ждать ответы генератора. Каждый вариант измерить заново при одинаковом тексте, настройках генерации и concurrency; оценить p95, RPS, CPU и GPU. Если очередь перейдёт к `text_embedding` или vLLM, отдельно проверять число CPU-экземпляров эмбеддинга, длину генерации и настройки GPU. Для ветки сообщения также начать с очереди BLS. Изменения конфигурации могут увеличить расход CPU/памяти и должны подтверждаться замером.
